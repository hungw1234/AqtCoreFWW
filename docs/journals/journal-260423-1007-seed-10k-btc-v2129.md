## The Brutal Truth

This looked simple on paper: seed 10k test users. Reality: multi-module synchronization, config guards, cross-boundary data access, and subtle concurrency bugs in idempotency logic. Plan review + red-team **saved 6-8 hours of rework**. Without it, shipped code would've crashed on restart (roles duplicate exception, false idempotency skip).

The frustration point: seeding should be straightforward, but architectural constraints (module isolation + multi-tenant + no cross-module DbContext) forced raw Dapper SQL bridge. Worth it for isolation, but felt clunky during implementation.

## Technical Details

### Cross-module pattern
Organization.Infrastructure needed Identity users. Couldn't inject OrgDbContext → Identity. Solution: Dapper raw SQL from Organization seeder:
```csharp
var users = dapperConnection.Query<IdentityUser>(
  "SELECT Id, Email, ... FROM identity.AspNetUsers WHERE Email LIKE @Pattern"
);
```
Rationale: preserve module boundary, avoid circular ref. Trade-off: raw SQL instead of ORM luxury.

### Config guard
```csharp
var requiredMinUsers = orgUnits.Count + DevReserveCount;
if (userCount < requiredMinUsers)
  throw new InvalidOperationException($"UserCount {userCount} < required {requiredMinUsers}");
```
Fails fast if config wrong. Caught during red-team before seeder ran.

### Idempotency = per-entity HashSet
**Lesson from v2.128**: count gate (`if (users.Count > 0) return`) breaks when other seeders add data.
Fixed: per-entity check:
```csharp
var existingEmails = users.Select(u => u.Email).ToHashSet();
var newUsers = btcUserList.Where(u => !existingEmails.Contains(u.Email)).ToList();
```
Restart: loads existing emails, skips only duplicates. Count-agnostic idempotency.

## What We Tried

1. **Monolithic seeder**: Rejected early. Split into 2 seeders (Identity + Organization) to respect module boundaries.
2. **OrgDbContext in Identity**: Sketched, failed design review. Cross-module dep forbidden. Dapper bridge chosen.
3. **Count gate for idempotency**: v2.128 lesson: broke under concurrent seeders. Switched to per-entity HashSet.
4. **Batched SaveChanges**: Tried 2-loop (roles then users), then atomic batch. Atomic per-100 users faster + safer.

## Root Cause Analysis: Bugs Caught

### 5 bugs caught by red-team (plan review, cost: $0 fix)
1. **C1 - Cross-module ref mismatch**: RoleId FK in UserRole didn't match actual seed roles. Caught before code written.
2. **C2 - DbSet name**: `DbSet<IdentityRole>` vs `IdentityRoles` confusion. Code-gen mismatch. Red-team verified signature.
3. **C3 - ClassificationLevel missing**: BTC roles need `ClassificationLevel` (VN PKI). Not in role seed initially.
4. **C4 - Bogus config**: Library import missing, seed would NRE. Caught in plan.
5. **C5 - Pass 1 resume crash**: OrgUnit.Lead missing exception if OU has no Lead. Guard added.

### 2 bugs caught by tester (cost: 2 reruns)
1. **Roles NormalizedName duplicate**: RoleManager threw on second run. Tester: restart from clean, add master guard `if (role exists by NormalizedName) skip`. Verified idempotency works.
2. **BtcAssignmentSeeder false skip**: Used `_context.Users.Count()` (tenant-wide), not BTC-specific count. Idempotency gate skipped even though BTC assignments empty. Fix: per-role HashSet + explicit BTC filter.

### 3 bugs caught by code-reviewer (post-test latent)
1. **H-1 (Pass 3 truncation)**: If `UserCount < 1268`, Pass 3 dev reserve would over-allocate. Guard added: `if (pass3Count > remaining) pass3Count = remaining`.
2. **M-1 (Pass 1 ignore UserCount)**: Pass 1 processed all OrgUnits regardless of userCount budget. Changed to: consume from budget per unit.
3. **M-3 (non-transactional 2-loop)**: Assignments loop didn't wrap in same transaction as SaveChanges. Fixed: atomic per-100 batch with explicit transaction scope.

## Lessons Learned

1. **Plan review + red-team ROI is 6-8x** — catching bugs before code costs $0 rework. Allocated 2 hours to plan review, saved 12-16 hours of test-debug-fix cycles. Do this first.

2. **Config guard > silent truncation** — throw early if inputs invalid. `if (userCount < required) throw` beats silent data loss.

3. **Per-entity idempotency > count gate** — HashSet approach survives concurrent seeders. v2.128 taught this (backlog reminder added).

4. **Atomic batch assignments + histories** — 3 SaveChanges (role, user, assignment) spread across 2 loops = race condition risk. Single batch per 100 users cleaner.

5. **Raw SQL bridges for cross-module data** — Dapper used judiciously (read-only, no DML) avoids circular DbContext dep without sacrificing module isolation.

6. **Test restarts matter** — idempotency visible only on 2nd run. First-run smoke masks bugs. Always restart.
