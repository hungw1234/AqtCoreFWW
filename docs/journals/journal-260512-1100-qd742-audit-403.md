## The Brutal Truth

The backlog row's premise ("10 failing tests, all 403") was lazy. Ran the tests and found **three completely different problems**:

1. **B1 (6 tests, 403):** `RtbfController` requires MFA. The test helper forgot to emit the `X-Test-MfaAt` header. One-line fix, exposed a gap in `TestSystemAdminPermissionBypassHandler` (only bypasses perms, not MFA).

2. **B2 (3 tests, "Invalid column name 'Id'"):** The `[audit].[tr_AuditLog_NoMutate]` trigger **does not exist**. Phase-06 migration regen dropped the original migration file (`20260501020000_AddAuditImmutabilityTrigger_M2`) and the regenerated `InitialCreateFoundationV1` never re-added the `CREATE TRIGGER` SQL. This is a **real production regression** — dev DB already broke, prod will break on the next migration deploy (from `a280d526` which had the trigger, to `f5124854^` which does not, then to `f5124854` which tries to assume it exists in `AuditLogImmutabilityTests`).

3. **B3 (1 test, 404 not 400):** The global-default `AuditRetentionPolicies` seed row is also missing — same Phase-06 regen loss. Entity is now T1 `long` PK, original seed was fixed-Guid. Handler does `GetByIdAsync(1)` and gets 404 instead of the expected concurrency-token 400.

## Technical Details

**B2 trigger loss:** The `CREATE OR ALTER TRIGGER [audit].[tr_AuditLog_NoMutate]` bypass contract is `SESSION_CONTEXT(N'audit_mutate_mode')` ∈ {`'archive'`, `'signature'`}. Verified byte-for-byte against `git show a280d526`. The regeneration happened at commits `1f344588` (drop 217 old migrations) + `fde9ec49` (regen + InitialCreateFoundationV1). The trigger SQL was lost because it lives in `.cs` migration files, not the EF model snapshot, so `dotnet ef migrations add` cannot recover it.

**B3 seed loss:** Original was `InsertData` in `20260501004056_AddAuditCategoryAndSeverity_M1` with hardcoded Guid Id. Post-Phase-04b the entity became T1 `long` PK. New migration uses `SET IDENTITY_INSERT ... ON; INSERT ...; SET IDENTITY_INSERT ... OFF;` with `Id=1` and a guard `IF NOT EXISTS (... WHERE TenantId IS NULL AND Category IS NULL)` for idempotency. The test const `GlobalDefaultPolicyId = 1L` remains valid.

**B1 test fix:** `WebAppFixture.TestAuthHandler` only injects `mfa_at` claim when the `X-Test-MfaAt` header is present (matches the convention in `SecurityIncidentsApiTests` and `NotificationEndpointsTests`). `CreateClientWithPermissions` builds a bespoke client and forgot the header.

## Decisions

1. **Restore raw SQL, not EF model:** The trigger is pure DDL and the seed is a one-time correction; both belong in migrations as `migrationBuilder.Sql(...)`. A future decision can move the seed to EF `HasData` if idempotency proves fragile, but for now, raw SQL is the correct surface (comment in the migration explains why).

2. **Use `IDENTITY_INSERT Id=1`:** Deterministic seed at `Id=1` so test const + idempotence work. Trade-off: can collide if an admin created a policy via API between regen and deploy. Code review flagged this as M1 (non-blocking) — add a one-line caveat to the migration header before merge.

3. **Empirical test run before fix path:** Tested first, then diagnosed. Memory note `phase7-b4-integration-audit-dapper-shipped` codified this; proved its value again (beat the "10× same bug" assumption by ~6× investigative time savings).

## Lessons Learned

1. **Migration regen sweeps lose hand-tuned artifacts.** The "drop all old migrations + regenerate" approach in Phase-06 silently deleted `CREATE TRIGGER` and `InsertData` SQL because those live in `.cs` files, not the model snapshot. A post-regen audit step (grep for `.Sql(` and `InsertData` in all migrations before the regen, compare to the new migration) would catch this. Alternatively, a compliance smoke test asserting `sys.triggers` contains `tr_AuditLog_NoMutate` + the global-default `AuditRetentionPolicies` row exists (code-review M3, backlog FU1).

2. **Test infra can mask root causes.** `AuditLogImmutabilityTests` hit "Invalid column name 'Id'" first, hiding the missing-trigger error. Only after fixing the T3 PK-column mistake (`WHERE MessageId`) did the missing trigger become visible. Always fix the *nearest* error first, but suspect secondary failures.

3. **Backlog row premises drift in hours.** The row was written as "10× 403" when actually it was 3 unrelated bugs. Premise was plausible at frame time, but empirical run (15 min) beat speculative fix (2-3h). Same pattern as memory `verify-fe-consumer-before-be-build` YAGNI closures.
