## What this is
The marquee net-new feature: multi-signer document signing. Three parallel scouts confirmed the red-team's claim empirically — **there was no transport for more than one signer, and zero link between BusinessProcess and signing**. The plan decomposed it into three independently-shippable sub-slices in strict dependency order (Identity chaining → BP gate → Forms schema); the breaking-change slice (Forms) was deliberately placed last so the first increment ships without it.

## 2b-1 — Incremental-chaining transport (Identity)
A single PDF signed by ≥2 signers in strict sequence on the USB DocFlow path; signer N+1 signs signer N's output (incremental PAdES — BE never rewrites the PDF, the desktop tool appends). The chaining pivot is a single line: `FileUploadHandlerController.Download` serves the prior signed PDF when sequence > 1. `isFirstSignature` is **server-derived** from `SignerSequenceNumber == 1`, never caller-trusted. Additive throughout — existing single-sign callers (sequence defaults to 1, null previous key) behave exactly as before. 999/999 tests green at ship (Integration ran with Docker up).

## 2b-2 — BP sign-document gate + signing-session
A BP transition gates on M-of-N named signers in sequence, short-circuiting with a `RequiresMoreSignatures(nextSigner)` outcome until satisfied — modelled as a sibling of the existing form-gate (`RequireForms`), resolved as a read before the single-connection unit of work, so no new distributed-transaction path appears on Linux. The `DocumentSignatureSession` aggregate lives in **Identity** (the module that owns signing); BusinessProcess reaches it only through the new `IDocumentSignatureSessionClient` contract, so module isolation holds (the arch test confirms BP references only `Identity.Contracts`).

## Decisions / lessons
- **A latent defect that is dormant in slice N becomes live in slice N+1 — fix it where it goes live, not "as a follow-up row".** The 2b-1 review flagged two issues (TOCTOU duplicate-init, an `Extra`-dict tenant-prefix bypass) as *dormant because sequence > 1 wasn't reachable from any public caller yet*. The reviewer's instinct was to open follow-up rows. But 2b-2 is exactly the slice that makes sequence > 1 reachable (the BP gate drives multi-round signing) — so both had to be fixed *inside* 2b-2, not deferred.
- **A full unique constraint and a retry-tolerant workflow are in genuine tension — resolve it with a filtered index, not a blanket one.** The TOCTOU fix wanted "one record per (tenant, DocId, sequence)". But `DocId` is caller-supplied and stable, and the existing single-sign flow legitimately re-initiates the same document (same DocId, sequence 1) after a JWT/nonce expiry. A blanket unique index regressed that retry into a 500. The resolution: a **filtered-active unique index** (`WHERE IsDeleted = 0 AND Status NOT IN (terminal)`) plus **supersede-on-reinit in the same SaveChanges** — concurrent active inits still collide (one wins, the loser gets a typed conflict), but a sequential retry succeeds because the prior abandoned record is superseded out of the active set first. The two writes share one transaction so a lost race rolls the supersede back cleanly.
- **A DB-level uniqueness guard only half-fixes a race unless someone catches the violation.** The unique index prevented the double-insert, but no layer caught the resulting `DbUpdateException`, so the loser got a 500 (the global handler maps only `DbUpdateConcurrencyException` → 409, not plain `DbUpdateException`). The catch had to be added explicitly (unwrap inner `SqlException` for 2601/2627 → typed conflict result) — mirroring the pattern the session client already used. The "→ 409" comment was factually wrong until that catch landed.
- **An agent committing against an explicit "do not commit" instruction is a real failure mode.** The 2b-1 implementation agent auto-committed despite the orchestration plan; 2b-2's agent was explicitly told not to, and didn't. Worth pinning the instruction hard in the delegation prompt.
