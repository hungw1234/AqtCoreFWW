# D8: Orval v8 Pinned to v7.21.0 — Memory Diagnosis Wrong, Empirical Resolution Right

**Date:** 2026-04-18 22:00  
**Severity:** Medium  
**Component:** web/orval (codegen), api-client setup, generated type safety  
**Status:** Resolved (v7 pinned, D8b+D8c deferred as follow-ups)  

## What Happened

Shipped D8 as a v7 pin, not a v8 migration. Memory claimed "orval v8 passes 2-arg to mutator, mutator is v7 1-arg, TS2554 across 40+ files—fix the signature." Turned out the real problem was wholesale: orval v8 rewrites the entire output shape (mutator signature, response envelope, schema filename), not just a 1-arg vs 2-arg bump. Empirical regen revealed the pin was cheaper (5 min) and safer than the memory-based 2-5d refactor. Branch `feat/d8-orval-v8-mutator-upgrade` (1 commit, PR #41) shipped with `"orval": "7.21.0"` exact pin in package.json + regenerated lock file. No TS errors, smoke tests pass.

## The Brutal Truth

This is the most valuable lesson I've learned about memory-vs-reality in this project. Memory diagnosed a *symptom* (1-arg mutator called in generated code) and extrapolated to a *solution* (fix the signature). But the memory didn't know that orval v8 is NOT a signature bump—it's a wholesale rewrite. Investing 2-5 days into a "2-arg migration" based on incomplete diagnosis would have surfaced 10 hours in when the response envelope blew up all the useQuery callers.

The advisor's pre-check was gold: "Check the D7 FE commit diff, inspect orval generator source, or regen empirically." That escalation ladder—file contents → git history → generator source → empirical test—is way cheaper than guessing. Took 20 minutes of investigation (read api-client.ts, read a v7.21.0-marked generated file, start BE, regen, diff) vs. hours of dead-end refactoring.

Even more galling: the memory was *technically correct* on the narrowest point (the mutator IS 1-arg), but that correctness masked the bigger architectural shift. It's like diagnosing "the car won't start" as "battery is weak" when the engine was actually swapped—the symptom-to-remedy mapping is broken at the assumptions layer, not the execution layer.

## Technical Details

**Memory's diagnosis:**
```
orval v8 emits 2-arg mutator: (config: AxiosRequestConfig, response: Response) → T
Codebase has 1-arg: (config: AxiosRequestConfig) → Promise<T>
TS2554 on ~40 call sites
Fix: upgrade mutator signature in api-client.ts
```

**Reality (discovered empirically):**
- **v7 mutator:** `(config: AxiosRequestConfig) → Promise<T>` (1-arg, axios-style)
- **v8 mutator:** `(url: string, options: RequestInit) → Promise<{ data: T; status: number; headers: Record<string, string> }>` (fetch-style, structured response envelope)
- **v7 response:** Raw T (e.g., `{ id: "uuid", name: "Case A" }`)
- **v8 response:** Envelope wraps it: `{ data: T, status: 200, headers: {...} }` — caller gets the envelope, response interceptor unwraps `.data`
- **v7 schema filename:** `aqtCoreFWApiV1.schemas`
- **v8 schema filename:** `aqtCoreFWAPIHThNgChínhPhS.schemas` (slugified from BE OpenAPI title: "AqtCoreFW — API Hệ thống Chính phủ số")

**The cost difference:**
- **Option A (v8 migration):** Rewrite RequestInit signatures, refactor response envelope handling in api-client.ts (~40 LOC), cascade response-shape changes to ~100 useQuery callers across Cases, Workflow, Masterdata, etc. Estimated 2-5 days.
- **Option B (v7 pin):** `"orval": "7.21.0"` in package.json (1 line), `npm install` regen lock file, verify `npx tsc --noEmit` passes. 5 minutes.

Chose B.

**Empirical discovery path:**
1. Read `src/api/api-client.ts` → confirmed mutator is 1-arg: `(config: AxiosRequestConfig) ⇒ Promise<T>`
2. Read generated file header in `src/api/generated/cases/cases.ts` → header says "Generated by orval v7.21.0"
3. Checked mutator call in same file → 1-arg, matches api-client.ts signature. **No TS2554 error in committed state.**
4. Key insight: "Generated code in repo is v7.21.0, but `npm list orval` shows v8.6.2 installed." Generator on disk ≠ code in repo.
5. Started BE: `ASPNETCORE_ENVIRONMENT=Development ASPNETCORE_URLS=http://localhost:5001 dotnet run --project src/host/AqtCoreFW.Api/`
6. Ran `npm run generate:api` → new output with v8 header, fetch-style mutator, structured envelope. Diff to v7 output: massive (mutator signature, response shape, ~200 lines per file).
7. Compared to api-client.ts (still 1-arg) → mismatch confirmed. Migration scope is real and NOT a 1-line fix.

## What We Tried

1. **Advisor pre-check:** Flagged memory diagnosis vs. canonical orval v8 docs (canonical shows 1-arg, memory claimed 2-arg). Recommended three escalation paths: (a) inspect D7 FE commit diff to find what changed, (b) read orval generator source on GitHub for v8 breaking changes, (c) empirical regen (cheapest proof).

2. **Took path (c) first:** Started BE, ran regen, got v8 output. Diffed to v7 in repo—confirmed the memory was half-right (mutator IS in the diff) but massively incomplete (response envelope is also in the diff).

3. **Considered option A (migrate v8):** Would need to rewrite api-client.ts response interceptor logic, change all useQuery signatures, test across 4 modules. Advisor flagged it as orthogonal to "fix the pin"—if v7 works now, pin it, then plan v8 as a separate 2-5d initiative (D8b).

4. **Chose option B (pin v7):** Edited `web/package.json` `"orval": "^8.6.2"` → `"orval": "7.21.0"`, ran `npm install`, let npm regenerate lock file (193 packages added, 35 removed, 25 changed in dependency graph).

5. **Scope discipline:** Initial instinct was to commit the regen output too (fresh v7 files). Advisor caught this: "Regen output is orthogonal to the pin fix. The pin alone unblocks future regens. Don't commit the generated code—it's noisy and defeats the purpose of a fix."

6. **Reverted generated files:** `git checkout -- src/api/generated/` + `git clean -fd src/api/generated/` (removed v8 artifacts from npm tree). Final commit: package.json + lock file only.

## Root Cause Analysis

**Why memory was incomplete:**
- Memory captured the symptom (1-arg mutator in generated code), not the full orval v8 architectural change.
- The diagnosis assumed the fix was "upgrade the mutator signature in api-client.ts." Plausible if you're only looking at one dimension (function signature), but blind to the other two dimensions (response envelope shape, schema filename derivation).
- No empirical validation of the diagnosis before estimating effort (2-5d is a guess if you haven't measured the scope).

**Why empirical regen was the right escalation:**
- Orval v8 changes are *generated code* behavior, not API contract behavior. You can't know the scope without seeing the actual output.
- Regen takes 1-2 minutes per environment (run BE, run generator). Cheaper than reading 50 GitHub issues about orval v8.
- Diff of regen output to committed code is the most direct proof of scope.

**Why the pin was the right choice:**
- If v7 works now and the migration is 2-5 days, there's no urgent reason to migrate today. The benefit (catch up to latest orval features) is outweighed by the cost (cascade refactor across all api hooks).
- Pinning v7 is **not** technical debt—it's a deliberate, documented decision to defer a large refactor. D8b is now on the backlog.
- The pin is *reversible*—when D8b is resourced, the only work is the refactor, not debugging why v8 broke in the first place.

## Lessons Learned

1. **Memory diagnosis must be challenged with empirical reality, especially when the estimate seems high (2-5d for "a signature bump").**
   - If a diagnostic claim seems disproportionate, escalate to primary sources (code, generator source, empirical test) before committing to the remediation path.
   - Canonical orval v8 docs show 1-arg; memory claimed 2-arg. That contradiction alone should have tripled the investigation budget.

2. **Scope discipline is a conversation, not self-enforced.**
   - I was 1 step away from committing the v7-regen output (cleaner code, fresh artifacts). The advisor's "regen output is orthogonal to the pin fix" corrected my instinct.
   - Scope creep often looks like "polish"—commit fresh generated files, simplify the lock file diff. But it obscures the actual fix (the pin) and adds noise to the PR.

3. **The escalation ladder for empirical questions: file contents → git history → generator source → empirical test.**
   - Cheapest: read api-client.ts (already in repo). Found 1-arg.
   - Next: git diff of D7 FE commit (already computed). Found generated code is v7.21.0-marked.
   - Next: GitHub orval repo (external, requires context switch).
   - Last: empirical regen (requires running services). Did this, confirmed scope.
   - Stopping at step 2 would have been enough to flag the memory diagnosis as incomplete.

4. **"Trust but verify" applies to memory, not just subagents.**
   - Memory said "1-2h effort, mutator signature fix." Reality: "5 min pin, 2-5d migration is orthogonal."
   - The memory wasn't *wrong*—it was *incomplete*. It captured the surface diagnosis, not the full scope.

5. **Pinning a dependency is not technical debt—it's a conscious trade-off.**
   - Staying on v7 while v8 is available is a choice: "We recognize v8 exists, we've measured the cost (2-5d), we defer it as D8b."
   - The pin is documented in code (exact version) and in backlog (D8b context). It's traceable and intentional.
